# 账号登录与安全

在「账号与团队」点击「登录与安全」。输入邮箱、密码和可选的现有验证器密钥，选择操作。2FA 密钥留空时，使用本机已保存的该邮箱密钥（先看「2FA 密钥备份」，其次是团队购买信息里的母号 2FA）；都没有时，官方要求验证码就由你在窗口里输入。

## OAuth 授权

打开本机独立的普通 Chrome 窗口，在官方页面填写邮箱、密码和明确识别的验证器动态码。每类资料最多自动提交一次。遇到邮箱验证码、安全挑战、授权同意或未知页面时停止填写，等待使用者在窗口中继续。回调返回后核对 state、PKCE、邮箱、工作区及本地账号快照，成功才保存授权。

手动输入的密码和验证器密钥仅在本次任务内存使用，不写数据库、操作记录或浏览器存储。不会自动检查额度或推送远端。保留现有账号团队关系；新邮箱仅在成功授权后建立本地待命档案。

每次只启动一个浏览器任务，使用已有账号的固定代理；不支持的代理明确失败，不回退直连。关闭工具抽屉不停止任务；「停止浏览器任务」关闭独立窗口。任务最多等待十分钟，重启不自动重放。

## 重设 2FA

选择「重设 2FA（自动换绑并保存新密钥）」并勾选确认。程序用同一个普通 Chrome 窗口登录 chatgpt.com，检测到登录会话后，在这个页面会话内向官方接口依次：

1. 读取会话，核对登录的邮箱就是所填邮箱（不一致就停止，不发送任何更改）；
2. 读取官方 2FA 状态；
3. 停用旧验证器（账号尚未开启 2FA 时跳过，等于直接开启）；
4. 生成新密钥；
5. 用新密钥算出的动态码激活；
6. 再读一次状态，核对新因子已生效。

请求由已登录的官方页面自己发出，沿用页面的 Cookie、设备标识和网络出口；程序不做协议登录，也不处理验证码或人机验证，这些仍由你在窗口里完成。此入口不要求账号的刷新权在本机（不读取也不改写已保存的授权）。

每个会改变账号的请求发出之前，先把加密恢复记录写进本机数据库：新密钥在激活前已经落库；激活被官方确认的同一次写入里，它成为该邮箱的 2FA 密钥备份，并写入该邮箱名下团队的母号 2FA。核对生效后恢复记录不再保留密钥。任务记录、状态接口和日志都不含密钥、验证码或令牌。

成功后可在任务结果或「2FA 密钥备份」复制、下载新密钥，请同步到你自己的验证器或密码库。换绑一旦开始发送更改，「停止浏览器任务」不会打断正在进行的请求，最多等约 100 秒让流程走到可恢复的节点。

### 中断与恢复

响应丢失、官方报错、窗口被关闭或服务重启都可能让流程停在中间。恢复记录按邮箱保存：

| 状态 | 含义 | 再次发起「重设 2FA」时 |
| --- | --- | --- |
| 已开始，尚未取得新密钥 | 旧 2FA 可能已停用，账号可能暂时没有 2FA | 重新读取官方状态后从头继续 |
| 新密钥待激活 | 新密钥已保存，官方明确没有激活 | 用已保存的密钥和激活会话继续，不重新生成 |
| 激活结果未知 | 激活请求已发出，结果不明 | 先核对官方状态；确认未生效才重发激活 |
| 已激活，待核对 | 官方已确认激活，新密钥已是备份 | 只核对状态 |

存在未完成记录时不会生成第二把密钥。后两种状态下新密钥可能已经生效，登录用的验证码改由它生成；如果登录时官方直接接受了这个验证码，也视为新密钥已生效。官方显示已开启 2FA 但无法对应到本次密钥时，程序不发送任何更改，请导出候选密钥自行核对。

在「2FA 密钥备份 → 自动换绑记录」可按邮箱查询状态、导出候选密钥或放弃记录。放弃只关闭本地记录，不撤销官方已发生的变更；含密钥的记录会加密归档而不是删除，激活结果未知时必须先导出候选密钥才能放弃。有未完成记录的邮箱暂时不能写入手动备份。

## 官方安全设置与退出会话

这两项在官方网页登录后打开安全设置，最终操作由使用者在官方窗口完成。程序不替使用者确认，也不读取官方页面上显示的内容。观察到当前窗口退出不等于全部会话已退出，因此结果保持待核对。

## 2FA 密钥备份

「重设 2FA」的新密钥自动保存在这里，标记为“官方已激活，状态待核对”或“官方已激活并核对生效”。

在官方页面手动换绑后，也可以在这里输入新密钥并确认对应邮箱：备份加密存入本机数据库，标记为“用户确认，未经官方验证”，不修改远端账号。

按邮箱复制或下载会取得明文密钥。不要把明文文件提交到代码库或公开分享。

2026-11-20（重设 2FA）：新增离线测试覆盖协议请求形状与错误分类、换绑状态机在每一步丢失响应／报错／本地写入失败后的恢复、不重复生成密钥、密钥不出现在任务记录和数据库明文中、浏览器内请求的来源限制、HTTP 鉴权与同源校验。测试只用合成账号和模拟官方接口，外部网络尝试为零；没有对真实账号执行过换绑，首次真实使用请先用一个不重要的账号验证，并留意官方接口行为可能变化。

本实现没有接入 Bridge 的协议登录或验证码求解，也未发布批量并发、代理轮换或模型测试。换绑请求形状参考 gpt-auth-bridge（MIT，许可证见 [third-party](third-party/gpt-auth-bridge-LICENSE.txt)）。原 Bridge 开发草稿独立保留。

## 协议登录（无浏览器，可并行）

「登录与安全」新增「协议登录（无浏览器）」标签页，通过本机 GPTAuthBridge（默认 `http://127.0.0.1:4173`）用邮箱、密码和 2FA 密钥协议登录，不打开浏览器，可多个账号并行（授权桥并发上限 10）。

- **批量登录并导入授权**：每行一个 `邮箱----密码----2FA密钥`（2FA 可省略，也支持 `——` 或 `|`）。登录成功的账号导入个人授权（访问令牌、刷新令牌），之后可在账号页检查额度、推送 Sub2API。由远端托管刷新的账号会跳过。
- **协议重设 2FA**：先协议登录取得网页会话，再在该会话内执行与「重设 2FA」相同的持久化换绑流程（停用旧因子 → 生成 → 激活 → 核对），新密钥加密保存在「2FA 密钥」。

配置（`.env`）：`AUTH_BRIDGE_ENABLED=true` 开启；`AUTH_BRIDGE_URL` 改地址（仅本机回环）；`AUTH_BRIDGE_PROXY` 是账号没有固定代理时授权桥访问官方用的代理；`AUTH_BRIDGE_CONCURRENCY` 默认 5。授权桥未启动时页面会提示不可用，不影响其它功能。

验收：2026-11-20 用真实账号完成协议登录、导入授权和协议重设 2FA（新密钥再次登录验证通过）；离线测试 961 项，失败项与改动前基线完全一致。
